# Bring-your-own-key LLM: threat model and key handling

The app has no server-side secrets. The optional "Explain my plan" summary is generated by
the **browser calling the user's chosen provider directly** (Anthropic, OpenAI or Google
Gemini) with a key the user pastes in Settings. This note records how that key is protected.
Implementation: `lib/ai/key-vault.ts`, `lib/ai/providers/*`, `lib/ai/stream-narrative.ts`,
`lib/security/headers.ts`. Context: [history entry](../history/2026-11-14-remove-accounts-local-first-byok.md).

## Threats and defences

| # | Threat | Defence |
|---|--------|---------|
| 1 | Someone reads browser storage, a profile copy or a backup | The key is **never stored in plaintext**. Default is session-only (memory). "Remember" stores an AES-256-GCM blob under a key derived from the user's passphrase with PBKDF2-SHA-256 (600 000 iterations, random 16-byte salt, fresh 12-byte IV). Not in backups, URLs or exports. |
| 2 | XSS / a malicious dependency tries to exfiltrate the key | CSP `connect-src` is pinned to `'self'`, the three provider origins  — no wildcards — so injected script cannot send the key to an attacker's host. No third-party script origins, `frame-src 'none'`, nonce + `strict-dynamic`. |
| 3 | The key leaks through logs, errors, URLs or the DOM | Key only in request **headers** (Gemini uses `x-goog-api-key`, never `?key=`). Provider error text is never shown — `ProviderError` has fixed messages (providers echo masked keys in 401 bodies). No `console.*` in `lib/ai` / `components/ai`. Inputs are cleared after save; the unlocked key lives only in a module closure. |
| 4 | A tampered or swapped stored blob | AES-GCM authentication; the provider is bound in as additional data; iteration counts outside 100 k–5 M are rejected. Wrong passphrase and tampering are indistinguishable. |
| 5 | Request redirected to another host / cookies sent | `providerFetch` pins the origin, uses `credentials: "omit"`, `redirect: "error"`, `referrerPolicy: "no-referrer"`, `cache: "no-store"`, and a 60 s timeout. |
| 6 | Runaway cost | Hard `max_tokens` cap per request; user cancel (`Stop`); aborted on navigation. |
| 7 | An unlocked key sitting in an abandoned page | Remembered keys re-lock after 15 min idle and when a page is restored from the back/forward cache. |

## Residual risk (be honest about it)

A script running **on this origin while the vault is unlocked** can still ask for the key and
make provider calls. CSP stops it exfiltrating the key, but not spending it. No browser-only
scheme fully closes this: a non-extractable `CryptoKey` can still be *used* by such a script,
so it is not offered as a "secure" mode. Mitigations are layered: strict CSP, no third-party
scripts, minimal dependencies (lockfile + `pnpm audit` in CI), session-only default, and
Settings tells users to create a **dedicated, spend-limited key** they can revoke.

## Rules for future changes (enforced where noted)

1. The key **must not** be persisted, logged, exported, put in a URL, or held in a Zustand
   store / React context / DOM. *(`lib/ai/key-isolation.test.ts`)*
2. `lib/ai/key-vault.ts` is imported only by the AI layer and its settings/unlock UI, never by
   stores, calculations or utils. *(same test)*
3. Provider clients receive the key as an argument and go through `providerFetch`.
4. Adding a provider means adding its origin to `PROVIDER_ORIGINS` **and** updating the exact
   `connect-src` assertion in `lib/security/headers.test.ts` — the CSP must never silently grow.
5. Never add a third-party script origin to `script-src`.
6. Never show provider response bodies to the user.
7. Review `lib/ai/model-tiers.ts` model ids against provider docs when touching it.

## Privacy note

Generating a summary sends balances, contributions, ages and goals (the prompt in
`lib/ai/plan-narrative-prompt.ts`) from the browser to the provider, under that provider's
terms — never to us. Income and inflation fields that the prompt does not use are not sent.
The Overview card says this next to the button.
